# 04 — M1: XNU escribiendo texto en manaus

Objetivo de la fase: **el teléfono muestra texto del kernel**, sin userland, sin
storage y sin GUI. Es el primer hito que demuestra que la plataforma está bien.

## 0. Antes de empezar

- `hw/manaus.hw.json` completo (`python3 tools/mkadt-manaus.py --check`).
- `dtb/mt6879.dtb` extraído de la partición stock. El DTB vive en
  `vendor_boot_b` (header v4), no en `boot_b`:

  ```bash
  python3 tools/bootimg.py info   vendor_boot_b.img
  python3 tools/bootimg.py unpack vendor_boot_b.img dtb/stock
  # -> dtb/stock/dtb
  ```

  `tools/bootimg.py` entiende header v0–v4 y vendor_boot v3/v4, sin SDK de
  Android. Si el DTB sale vacío, se está mirando la partición equivocada.
- **Backup verificado de `boot_b` y `vendor_boot_b`**: `tools/bootimg.py info`
  tiene que imprimir un `header_version` y tamaños coherentes. Sin esto no se
  flashea nada (este LK no tiene `fastboot boot`). **Hecho el 2026-11-08**:
  `boot_b.img` (67,108,864 B,
  `sha256=bbc67027a08cb26bc6f28d2bbfce96639ed36c87e1992c4586eeb745b7ee30a9`) y
  `vendor_boot_b.img` (67,108,864 B,
  `sha256=dc77a35891e79b145128d7847f1a8fa1d23e3b071bec96145d5b1d9266f4e653`),
  con el mismo hash en el teléfono y en el PC.
- El `dtb` de `vendor_boot_b` es un **DTBO** (`0xd7b7ab1e`), no un FDT: envuelve
  un único FDT de 249,036 B (`0xd00dfeed`) en un blob de 249,100 B. Para
  reproducir el layout stock hay que pasar ese blob DTBO completo, no el FDT
  extraído (`tools/dtbo.py extract`).
- Decidido el canal de consola: FB de LK o UART (ver M0).

## 0.1 Compilar el kernel en CI (macOS 14 ya no existe)

El workflow `xnu-manaus.yml` compila xnu-8796 en un runner de GitHub. Ojo:

- **Los runners `macos-14` se retiraron el 2026-11-02.** Cualquier workflow que
  los pida muere en 1 s con
  `The configuration 'macos-14-arm64-us-default' is not supported`.
  `xnu.yml` (el de sweet, sin tocar) sigue con `macos-14`: está roto *upstream*.
- `macos-15` es arm64 y solo trae **Xcode 16.0 – 16.4 y 26.x**; ya no hay
  Xcode 15.x en ningún runner. El workflow elige el **más antiguo**
  (`XCODE_VERSION: 16.0`) porque es el más cercano al 15.x con el que se
  diseñó xnu-8796.
- El único trozo del toolchain que **no** se compila desde fuente es `iig`
  (IOKit interface generator, usado solo por `iokit/DriverKit/Makefile`).
  Un `iig` demasiado nuevo generaría código para una ABI posterior a 8796
  (por ejemplo `IORPC.kernelContent`, que 8796 no tiene). Con **Xcode 16.0
  funciona**; si algún día falla en `iokit/DriverKit/*.iig.cpp`, se arregla con
  un parche de compatibilidad nuevo en `xnu/patches-manaus/` (sin tocar la
  serie base): añadir el campo que falte en `iokit/DriverKit/IORPC.h`.
- **Verificado:** run
  [42134881143](https://github.com/vizPilot/ios-manaus/actions/runs/42134881143)
  (commit `339511a`, Xcode 16.0, `DEVELOPMENT ARM64 SWEET`): build verde en
  **8,8 min**, artefactos `xnu-manaus-kernel` (60,4 MB) y
  `xnu-manaus-buildtree` (23,2 MB).
- **Verificado con guarda:** run
  [42136147024](https://github.com/vizPilot/ios-manaus/actions/runs/42136147024)
  (commit `8b34cf5`): verde, 12,5 min (cola de `macos-15` arm64). El paso
  `Collect` publica como anotación `notice` el kernel real, legible sin token:

  ```
  kernel.development.sweet 17188640 bytes
  sha256=493f08ce3509ba43f6df96f1cb3828c82c3270e4f2ac1b34a105b40daf8be356
  ```

  Si el build "tuviera éxito" sin instalar kernel, `Collect` falla con
  `::error title=no kernel::` en vez de dejar pasar un artefacto vacío. Ese es
  el kernel de M1: se descarga con login, y el `sha256` sirve de referencia
  para comprobar que lo empaquetado es lo compilado.
- El KDK 13.5 (headers del kernel de macOS 13.5) se descarga del manifiesto de
  dortania dentro de `build.sh`; eso no depende del runner.
- Los logs de Actions **no** son públicos sin token. Para leer errores desde
  fuera está el paso `Report build errors as annotations`: publica las primeras
  líneas `error:` y la cola del log como anotaciones del check run, que sí se
  leen sin autenticación en
  `https://api.github.com/repos/<owner>/<repo>/check-runs/<id>/annotations`.

```bash

# y ver el resultado sin gh:
curl -s https://api.github.com/repos/vizPilot/ios-manaus/actions/runs?per_page=3
```

## 1. Generar el ADT

```bash
python3 tools/mkadt-manaus.py --check --hw hw/manaus.hw.json      # debe salir 0
python3 tools/mkadt-manaus.py shim/out/manaus.adt --hw hw/manaus.hw.json --dump
```

Qué tiene que salir en el dump:

- `chosen/display-scale = 3` y canvas 1125×2436 (iPhone X lógico).
- `arm-io/gic` con GICD/GICR **restados** `soc_base` (el `ranges` de `arm-io`
  los vuelve a sumar).
- `cpus/cpuN/reg` = MPIDR real, no 0..7 inventado.
- `sweet-ufs` con `mediatek,mt8183-ufshci` (aún no se usa, pero debe estar).
- `/product` ausente mientras no exista `research/ipsw-x/d22ap.adt`: es normal,
  MobileGestalt lo necesita recién en M3.

## 2. Compilar el shim

`shim/build.sh` compila `start.S shim.c console.c mmu.c fdt.c loader.c ufs.c` y
**además** empaqueta un boot.img v2 con el DTB de sweet. Para manaus:

1. compilar los objetos (`bash shim/build.sh` sin argumento sirve para probar
   que compila);
2. ignorar su `mkbootimg` y empaquetar con `tools/mkbootimg-manaus.sh`.

Cambios del shim **ya hechos** (2026-11-07):

| Archivo | Cambio |
| --- | --- |
| `shim/console.c`, `shim/console.h` | `con_init()` lee `atag,videolfb-fb_base_l` y `vramSize` del FDT vivo; `struct fb_info` se pasa a `con_clear`, `mmu_enable`, `loader_boot` (`ba->Video`) y `mmu_probe`; quedan fallbacks de compilación |
| `shim/mmu.c`, `shim/mmu.h` | el bloque de 32 MiB del FB vivo se mapea Normal-NC; ya no se usa `0x9c000000` |
| `shim/shim.c`, `shim/loader.c` | `boot_args.Video` sale del FB vivo; el payload es el ramdisk crudo de `tools/mkpayload.py` |
| `shim/build.sh` | compila con `-Wall -Wextra`, 0 relocaciones ABS64 y enlaza `out/Image` |
| `shim/start.S` | sigue **sin** bajar de EL2 a EL1: si el primer arranque imprime `EL = 2`, ese es el siguiente cambio |

`shim/ufs.c` no se usa en M1; queda para M3. El mapa de RAM sale de
`hw/manaus.hw.json` (`ram.base`/`ram.size`), no de `memory@*`.

## 3. Empaquetar payload y boot image

```bash
mkdir -p shim/out
python3 tools/mkpayload.py xnu/out/kernel.development.sweet shim/out/manaus.adt shim/out/payload.bin \
  --cmdline 'debug=0xc serial=3 cpus=1 keepsyms=1 -enable_kprintf_spam -noprogress ignition_level=1 launchd_unsecure_cache=1 wdt=-1 sweetfb_noconsole=1 sweetfb_hz=30'

# v4 por defecto: misma forma que el boot.img stock (kernel en boot,
# ramdisk+dtb en vendor_boot). Escribe dos particiones.
tools/mkbootimg-manaus.sh shim/out/Image shim/out/payload.bin dtb/mt6879.dtb shim/out

# alternativa de una sola partición, solo si v4 no arranca:
tools/mkbootimg-manaus.sh shim/out/Image shim/out/payload.bin dtb/mt6879.dtb shim/out --mode v2
```

El script imprime el header real de cada imagen (via `tools/bootimg.py`) y su
`sha256`; eso es lo que hay que mirar antes de flashear, no el mensaje de
`mkbootimg`. `bash tools/test-mkbootimg.sh` comprueba el empaquetador completo
en local con bytes aleatorios (kernel, dtb y ramdisk vuelven idénticos).

Sin `rd=ufsroot0` todavía: en M1 no hay driver UFS ni root de iOS. El kernel
arranca y se queda en la consola.

## 4. Orden de pruebas (ya no hay `fastboot boot`)

Comprobado el 2026-11-05: este LK **no implementa** `fastboot boot`
(`hw/manaus.getvar.json`). El orden pasa a ser:

1. Respaldo de `boot_b` y `vendor_boot_b` en el PC, validado con
   `tools/bootimg.py info` (y guardando el `sha256`).
2. `--mode v4`: `fastboot flash boot_b` + `fastboot flash vendor_boot_b`.
   Es la forma que el LK ya arranca todos los días, así que es la primera que
   se prueba.
3. Si el LK rechaza v4 o se queda en el logo: restaurar las dos particiones y
   probar `--mode v2` (una sola partición).
4. Si no hay consola en pantalla pero sí UART: leer UART primero; el port sigue.

Cada intento se anota con hora, modo, imagen (`sha256`) y síntoma exacto. Un
"no arranca" sin distinguir "LK rechaza la imagen" de "kernel arranca y
cuelga" no sirve para el siguiente intento.

## 5. Qué tocar en `0004` (machine config)

Constantes de `pexpert/pexpert/arm64/SWEET.h` y `board_config.h`:

| Constante | Fuente |
| --- | --- |
| `GICD_BASE`, `GICR_BASE` | `hw/manaus.hw.json → gic` |
| `VTIMER_INTID` | `gic.virtual_timer_intid` |
| `TIMEBASE` | `timer.timebase_hz` |
| `PHYS_BASE`, `MEM_SIZE` | `ram.base`, `ram.size` |
| `MANAUS_ECID`, `CHIP_ID` (0x8015) | fijos (identidad iPhone X) |
| nº de CPUs y MPIDR | `cpus[]` |
| registro de UART | `serial@*` del FDT, si existe |
| stride de GICR | **no es constante**: `GICR_TYPER.VLPIS` (bit 1) en runtime, `0x40000` si está puesto (GICv4), si no `0x20000` |

El stride de GICR **no** se deduce del tamaño del `reg` del DT: el firmware
declara `0x200000` para 8 PEs, pero eso puede ser sobre-provisión y no distingue
GICv3 de GICv4. Tanto `shim/find_gicr()` como `pe_fiq/find_gicr_pe_base()` leen
`GICR_TYPER.VLPIS` del primer redistribuidor en cada arranque.

`start.s` y `sweet_cpu.c` (0065) usan esos valores para PSCI; MT6879 tiene dos
clusters, así que el orden de `cpus[]` y `cluster-id` importa.

## 6. SMP

`cpus=1` → `cpus=6` (A55) → `cpus=8` (A76). Si `cpus>1` cuelga, el fallo está en
`PSCI_CPU_ON`, en la pila de arranque o en el GIC redistributor de ese cluster;
no sigas a M3 con SMP roto.

## Criterio de salida de M1

- `fastboot boot` (o flash de boot) llega a XNU;
- consola legible con versión de kernel y líneas de arranque;
- 8 CPUs arrancadas (o 6, documentado);
- un log que se pueda leer después de un reinicio (M2).

## Riesgos específicos de MTK en esta fase

- **EL de entrada**: si LK entra en EL2, `start.s` debe bajar a EL1 antes de
  tocar `TTBR0_EL1`, `VBAR_EL1`, etc.
- **Magic de imagen MTK**: algunos LK esperan el header `0x58881688` delante de
  kernel/ramdisk. Si el arranque no llega ni al shim, probar a añadirlo.
- **Verificación de firma**: aunque el bootloader esté desbloqueado, Motorola
  puede exigir AVB en `boot`. En ese caso solo funciona flashear con
  `vbmeta` deshabilitado (`fastboot --disable-verification flash vbmeta ...`).
- **GIC seguro**: en sweet el timer va por Group 1 (IRQ), no FIQ. Confirmar en
  MT6879; si el secure firmware configura el GIC distinto, hay que ajustar
  `IGROUPR`/`IGRPENDR`.
- **16K de página**: si A76 no soporta el granule de 16K en esta implementación,
  XNU tendría que ir a 4K, que no es un cambio de configuración del repo.
